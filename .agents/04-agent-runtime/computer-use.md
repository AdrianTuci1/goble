# 04 — Computer use

**Status:** `[~]` partial: the whole path is wired end to end — tool → event → RDP source → the card in the conversation — the registry gives the desktop one writer at a time, the desktop can be closed, the desktop account is referenced by name and resolved on the host, and an opened desktop is drivable again under the recorded takeover rule (a party that wants to drive takes it; the user may take over from the agent at any time; the agent may never take over from the user). ## Problem

Some work has no shell answer: driving a browser, an installer, an IDE, a proprietary tool. The harness needs a **desktop** to act on, and the user needs to **see it and take it over** when the agent gets stuck or the step needs a human.

The desktop is on the **host**, not in our client. We never ship our renderer or a GUI of ours to the host: it runs `xrdp` and a session, and our client is the viewer. That is the whole reason the desktop is the one piece the install may pre-install (`TRACKER.md` R74) — an agent cannot bootstrap a graphical session through a tool call when there is no graphical session to bootstrap from.

## Where the frames go: a card in the conversation, not a window

The streamed desktop is drawn **in the conversation**, in the place the ask-user card takes when a turn stops to ask something. The user does not switch windows and does not leave the chat to look at it; the conversation reads the same whether the screen is shown or not.

## What already works

The path is complete, and reading it in order is the fastest way to see what is left:

| Step | Where |
| --- | --- |
| The agent asks for a desktop | tool `open_screen` — `goble-core/src/harness/definitions.rs:506`, dispatched at `harness/dispatch.rs:110` to `harness/handoff.rs::open_screen`, which validates `host`/`credential` and acknowledges; opening is the host's job |
| The tool call becomes an event | `HarnessServerEvent::screen_handoff_from_tool_call` (`goble-harness-protocol/src/lib.rs:189` and `:198`) builds a `ScreenHandoff` carrying a `RemoteScreenConfig` |
| The daemon carries it | `goble-daemon/src/state/events.rs:175` maps it to `DaemonEvent::ScreenHandoff` (`goble-daemon-protocol/src/lib.rs:224`) |
| The host opens the desktop | `goble-desktop-service/src/state/translator.rs:307` calls `DesktopState::open_remote_screen`, which resolves the credential the handoff names and registers `remote-xrdp:<host>:<port>`, then emits `screen:handoff` with the source id |
| The source is a real RDP client | `goble-screen-sdk::RdpRemoteSource::connect` — IronRDP behind the `rdp` feature, enabled by `goble-desktop-native` |
| The frame type and the seams | `goble-screen-core` — `ScreenFrame` (RGBA8), `ScreenCapturer`, `ScreenController`, `ScreenRegistry::{register_capturer, register_controller, unregister_source, capture, click, type_text, scroll, take_control, release_control}` (one writer at a time: `ControlHolder`; `unregister_source` is the close) |
| The element that draws a frame | `crates/goble-ui/src/elements/frame_view.rs` — holds the latest frame plus a `frame_seq`, so an unchanged frame is never re-uploaded |
| The card in the conversation | `goble-ui`'s `chat_view` `inline_screen` (a `FrameView` in the transcript) with `screen_link` / `on_open_screen_link` / `on_close_inline_screen` |
| The app's half | `app/src/root_view/events.rs:257` handles `screen:handoff`, selects the source and sets the conversation's `inline_screen_source`, which `root_view/rebuild.rs:117` turns into a frame snapshot for the transcript |

Warp-new has **no** remote-desktop streaming at all — its "computer use" is local screenshots plus synthetic OS input (`crates/computer_use`), agent-gated. So this surface has no reference implementation to copy; the frame element, the source and the card are ours.

## The takeover rule

Recorded here, enforced in `ScreenRegistry::take_control` (`crates/goble-screen-core/src/lib.rs`) so no call site can restate or bypass it, and named on the card the user sees (`view only` / `you are driving` / `the agent is driving`):

1. **The desktop starts view-only.** A handoff registers its capturer alone, so nobody holds its input (`control_holder` answers `None`).
2. **A party that wants to drive takes it.** Both input entry points take an unheld desktop, in `DesktopState` — where the two callers meet — rather than the registry taking implicitly: the app's own input (the screen pane's `ScreenState::click`/`type_text`/`scroll` → `DesktopState::click`/`type_text`/`scroll`) takes it for `User`, and the agent's computer-use path takes it for `Agent` (`DesktopState::click_as(ControlHolder::Agent, …)`, the entry point a harness tool call reaches through the daemon). The harness declares no `click`/`type_text` call yet, so what is proven today is that entry point.
3. **The user may take over from the agent at any time.** A `User` take replaces an `Agent` holder, so the user's next input is the user's desktop, and the card says `you are driving`.
4. **The agent may never take over from the user.** Its take stays refused with `ControlHeld { holder: User }` and its input fails with `source '…' is driven by the user: the agent cannot drive it until that control is released` — a clear error, never a silent no-op. The refused take is also the agent's **ask** for the desktop back: retry it once the user releases and it succeeds (rakazo answers the same request with HTTP 409 and records it as `waiting_takeover` on the run); surfacing that ask as the card's `waiting` state is still open, below.

## The three defects, in the order they matter

**1. There was no ownership — fixed in the registry (2026-09-17).** `RdpRemoteSource::connect` used to register a capturer **and** a controller, unconditionally (`crates/goble-screen-sdk/src/lib.rs:95-96`), so the moment a handoff landed the desktop was drivable by the agent and the user at the same time, with nothing arbitrating. `connect` now registers the capturer alone and hands the controller to its caller, and the registry carries the rule: `take_control` / `release_control` / `has_control` / `control_holder` over a `ControlHolder { User, Agent }`, with input holder-scoped, so one writer holds at a time and the other side's call is refused with `ScreenError::ControlHeld`. It is rakazo's rule, from the reference the user pointed at: **one writer at a time**. There, a takeover is refused with HTTP 409 while a run holds a live control lease, the lease has a TTL, and the agent can ask for the desktop back (`request_takeover`, surfacing as a `waiting_takeover` state); here the registry holds no lease table — the registered controller *is* the hold, and the refused take is the ask. **Who may take it from whom is now recorded and enforced** — [the takeover rule](#the-takeover-rule) above, 2026-09-17: the desktop starts view-only, both input entry points take it when it is unheld, the user may take it back from the agent at any time, and the agent's take stays refused. What is still open is the UI half — the card drawing the agent's refused take as its ask — listed in the Tasks below.

**2. Nothing closes the desktop — fixed in the registry and the app (2026-09-17).** `ScreenRegistry` had `register_capturer` and `register_controller` and no unregister for the capturer (`unregister_controller` existed for control, but nothing removed a source or its client), so a source lived for the life of the process: its IronRDP client thread stayed up, and the worker's `xrdp` session stayed open, after the turn that asked for it was over and after the user closed the card. On a provisioned host that is a running graphical session nobody is watching. `ScreenRegistry::unregister_source` now removes a source from **both** maps, dropping its capturer (and with it the frame buffer and, for a remote source, the client that feeds it) and its controller, whoever held it; `DesktopState::close_remote_screen` is the close path — it drops the controller parked for the source, unregisters it and announces `screen:closed`. **The trigger is not the run's end.** `DE::TraceFinished` ends the *turn*; the card is still in the conversation for the user to watch or take over, so closing there would blank a desktop somebody is still looking at, and a desktop the agent opened can outlive the turn that asked for it. The close comes from the **card's dismissal** and the **session's end** (the pane holding the conversation goes away), and both follow one rule — *the last viewer closes it*: `UiState::release_inline_screen` clears the pane's `inline_screen_source` and hands the source back only when **no** pane still names it, so dismissing one conversation's card never kills a stream another conversation is watching. The app drops the frames it held for the source (`ScreenState::close_source`) and the `screen:closed` drain clears any pane that still named it. The close also reaches the session itself, not only our registry: dropping the last `RdpController` sends the engine's in-band stop (`RdpInputEvent::Close`), which makes the RDP client send the shutdown request and end the connection — the part that ends the host's `xrdp` session rather than leaving it running. What is *not* verified is the far end of that: there is no xrdp host here, so that the server ends its session when the client goes is the server's behaviour, not something this repo observed.

**3. The desktop password was asked of the model — fixed (2026-09-17).** `open_screen`'s parameter schema carried `username` and `password` (`definitions.rs:513-514`), `screen_handoff_from_tool_call` copied them into `RemoteScreenConfig`, and that config travelled in the event to the host. So either the model was told the desktop password — breaking rule 1 of [`../03-workspace-model/shared-secrets-and-toml.md`](../03-workspace-model/shared-secrets-and-toml.md), "never the value", and putting it in the transcript — or the tool took a **credential name** and the host resolved the value where the RDP connection is built, the shape `run_command` already has with `{{credential:<name>}}`. It is now the second, and the account has no other route to the wire:

- **The schema names a credential.** `open_screen` takes `host` and `credential` (both required) plus the optional `port`/`width`/`height`; there is no `username` and no `password` in it, and the description says the value is resolved on the host when the connection is built. `handoff.rs::open_screen` refuses a call with no `credential` and refuses a `credential` that is not a single token (whitespace, a control character or a `:`) with a message to the model, so an account line pasted into that field cannot be echoed back in a tool result.
- **The event carries the reference.** `RemoteScreenConfig { host, port, credential, width, height }` (`goble-harness-types/src/lib.rs`) has no account field at all — `credential` is a **name**, and `RemoteScreenConfig::is_credential_name` is the one shape rule, applied by `screen_handoff_from_tool_call` before it builds the event and by the tool before it acknowledges. A config without a credential is not a handoff: the builder returns `None` (the caller surfaces a `ToolCallError`) and the field is not `serde(default)`, so a credential-less handoff fails to parse rather than defaulting to an empty account.
- **The value is resolved where the connection is built.** `DesktopState::open_remote_screen` (`goble-desktop-service/src/state/bootstrap.rs`) reads the credential through the same store the local credential path uses (`DesktopState::get_credential`, the store `run_command` expands from) before it builds the `goble_screen_sdk::RemoteConfig`, and that struct — the only place a value exists — is not serializable and never leaves the call. **The stored value is the account line `username:password`**: the name is a label (e.g. `xrdp-vps`), the account is the secret. Splitting on the first `:` keeps a password that contains one.
- **A missing credential fails the handoff; it does not open a desktop without one.** Every failure is loud and names the credential, never a value: a name that is not stored, a handoff that named none, a value that is not an account line, and an account line with an empty half. The translator's `Err` arm logs `screen handoff failed: <error>`. The alternative — opening with no credential — was rejected on the tree's own evidence: an xrdp server handed no account draws its own login window, whose bitmap update the IronRDP engine cannot decode, so the session ends with no frame (found while proving T4, [`../10-platform-and-performance/testing-and-ci.md`](../10-platform-and-performance/testing-and-ci.md)), which would register a source and hand the user a broken card instead of saying what is missing.

**Fixed — the handoff no longer throws the sheet open:** it used to open *both* the right-anchored screen sheet (`app/src/root_view/events.rs:259-261` set `s.open = true`) and the card in the conversation. The card is the surface; the sheet is the manual broadcast/computer-use surface and is now opened only by the user's own clicked link. See the task below.
