# 10 — Testing & CI

**Status:** `[~]` partial — the terminal conformance suite and the worker's suite are what CI runs
**Owns:** how the system is verified — which suites run, where, and what only a real host can settle. No product behaviour.
**Depends on:** [`README.md`](README.md), [`../GUIDE.md`](../GUIDE.md)

## Problem

The verification surface does not match the code's surface. The backend is the larger half of the repo (`goble-core`, `goble-desktop-service`, `goblin-worker`, the harness crates) and the only thing a push ran was the terminal conformance suite, so the worker's crates landed unverified — T2 gives the worker its own job, and T1 made that job's suite runnable at all (its end-to-end tests were `#[ignore]`d behind a hardcoded Linux path, and one assertion needing a runtime this repo does not build stays `#[ignore]`d with its command recorded). And two pieces of the remote direction were verified by nothing at all: the generated install script was a string that unit tests pattern-match, and `RdpRemoteSource::connect` has never been pointed at a live desktop. T3 has now run the script on a systemd host, which is the only reason the defect it found — the worker could not open its own task store — is known at all. T4 has now pointed the client at a live desktop, and that is the only reason the defect it found — the client never asked the server to log in, so no frame could ever arrive — is known at all.

A container is the right fixture for exactly those two, and for nothing else: the worker itself is an ordinary CLI process that builds and runs natively, so wrapping it in a container for its own tests buys nothing.

## What runs today

- `.github/workflows/ci.yml` — two jobs on `ubuntu-latest`. `terminal / conformance` is path-filtered to `crates/goble-terminal/**`, `vendor/alacritty_terminal/**`, `scripts/fetch-alacritty-terminal.sh` and `.config/nextest.toml`; it restores the vendored emulator and runs `cargo nextest run -p goble-terminal --profile ci`. `worker / e2e` (T2) is path-filtered to `crates/goblin-worker/**` and its `cargo metadata` closure — `crates/goble-core/**`, `crates/goble-daemon{,-client,-protocol}/**`, `crates/goble-harness-{internal,protocol,runtime,types}/**`, `crates/goble-replay/**`, `crates/goble-sandbox/**`, `crates/goble-workflow/**` — plus the same two shared paths, and runs `cargo nextest run -p goblin-worker --profile ci` with the terminal job's own setup steps. `on.<event>.paths` is workflow-scoped, not per job, so the file lists the union of the two sets and each job's group is exactly the crates it links.
- `.github/workflows/release.yml` — manual (`workflow_dispatch`); its `verify` job runs `cargo check --workspace --all-targets` and `cargo test --workspace` on `ubuntu-latest`, but only when a release is cut.
- Local: `cargo test -p <crate>` per crate. `crates/goblin-worker/tests/{worker_e2e,runtime_isolation_e2e}.rs` run in the worker's default suite since T1 and locate the worker binary with `env!("CARGO_BIN_EXE_goblin")`; the only `#[ignore]` left among them is `test_mcp_isolate_runtime_writes_per_workspace_markers` (run it with `cargo test -p goblin-worker --test runtime_isolation_e2e -- --ignored test_mcp_isolate_runtime_writes_per_workspace_markers`). `crates/goble-core/tests/install_systemd_e2e.rs` (T3) is `#[ignore]`d for the opposite reason — it needs the Docker daemon and a `--privileged` container — and its command is on the test and in the task below.

Nothing in that list exercises the install script or a remote desktop on a change, and T3 did not change that: a `--privileged` systemd container is a fixture a human starts, not something a push to `goble-core` should pull into CI, so the script's run stays the documented command below. A worker turn does run on any change to a crate the worker links, since T2.

T4's fixture is local for the same reason — Docker on the developer's machine, and `goble-screen-sdk` is not a crate the worker links — so its commands are documented rather than run on a push:

```bash
docker build -t goble-xrdp-host:t4 deploy/xrdp-host
docker run -d --name goble-t4-xrdp --shm-size=512m -p 127.0.0.1:13389:3389 goble-xrdp-host:t4
GOBLE_RDP_E2E_PORT=13389 cargo test -p goble-screen-sdk --features rdp --test rdp_e2e -- --ignored --nocapture
```

Leaving `GOBLE_RDP_E2E_PORT` unset makes the test start and stop its own container on a free port, which is one command: `cargo test -p goble-screen-sdk --features rdp --test rdp_e2e -- --ignored --nocapture`.

## Tasks

- [x] **T1 — Make the worker's end-to-end tests actually run.** `crates/goblin-worker/tests/worker_e2e.rs:14` and `runtime_isolation_e2e.rs:32` carried `#[ignore = "E2E: requires a built `goblin` binary (set GOBLIN_BIN); not run in the default suite"]` and both fell back to `/root/goble/target/release/goblin` (`worker_e2e.rs:19`, `runtime_isolation_e2e.rs:37`), a path that exists on no dev machine here — so the tests were not merely skipped, they could not pass as written. Both now locate the binary the way cargo intends, `env!("CARGO_BIN_EXE_goblin")`, which the build populates for integration tests of the owning package. `runtime_isolation_e2e` needs nothing this repo does not build for the flow itself (health, the WS push of a secret and an MCP server, two agent runs, one isolated workspace per run); the MCP half of it does — the worker neither installs nor spawns MCP servers — so those assertions live, verbatim, in `#[ignore]`d `test_mcp_isolate_runtime_writes_per_workspace_markers`, whose reason and command are on the test and in its module doc:
  - **Acceptance:** `cargo nextest run -p goblin-worker` (or `cargo test -p goblin-worker`) runs the previously ignored tests, and they pass, with no `#[ignore]` left in `worker_e2e.rs` and no absolute fallback path in either file. The one remaining `#[ignore]` (`runtime_isolation_e2e.rs`) is a documented fixture-less-runtime case, not a skipped file: `cargo test -p goblin-worker --test runtime_isolation_e2e -- --ignored test_mcp_isolate_runtime_writes_per_workspace_markers` (needs a worker-side MCP isolate runtime and `node` on `PATH`).
  - **Cannot settle:** nothing; this one is fully verifiable locally.

- [x] **T2 — Give the worker a CI job.** `.github/workflows/ci.yml` had one job, so a change to any crate the worker links landed unverified. It now carries `worker / e2e` beside `terminal / conformance`, running `cargo nextest run -p goblin-worker --profile ci` on `ubuntu-latest` with the terminal job's own setup steps rather than a parallel set. The filter is the worker's path-dependency closure read out of `cargo metadata` — `goblin-worker`, `goble-core` (which pulls `goble-sandbox`), `goble-daemon`, `goble-daemon-client`, `goble-daemon-protocol`, `goble-harness-{internal,protocol,runtime,types}`, `goble-replay`, `goble-workflow` — plus `.config/nextest.toml` and the workflow file. Because `on.<event>.paths` is workflow-scoped, the two jobs' crate sets are one union list, and the terminal job's paths are untouched. The vendored-emulator restore step stays in the worker job for the reason the terminal job already records: cargo loads every workspace member's manifest, so with `vendor/alacritty_terminal` absent `cargo nextest list -p goblin-worker` exits 102 on the missing path dependency.
  - **Acceptance:** `cargo nextest run -p goblin-worker --profile ci` → exit 0, 77 tests run / 77 passed / 1 skipped; `actionlint` exit 0 and the YAML loads to two jobs; no existing job's filter narrowed.
  - **Cannot settle:** the job executing on GitHub's `ubuntu-latest`. The command was run on this machine's macOS toolchain (nextest 0.9.144, installed with `cargo install cargo-nextest --locked --root /tmp/nextest-root` — into `/tmp`, never against the repo — because it is not installed here) and, as a Linux cross-check, in an `ubuntu:24.04` container; the runner image itself is not exercised until a push. Nextest is not installed on this machine now and it had no network on the 2026-09-17 re-check, so the job's literal command is currently un-runnable here: the runnable equivalent is `cargo test -p goblin-worker`.

- [x] **T3 — Verify the install script on a real systemd host.** `generate_install_script` (`crates/goble-core/src/provision.rs`) was only ever asserted on as text, so nothing knew whether the host it targets could run the result. It can now be executed. `deploy/systemd-host/Dockerfile` is a systemd-as-PID-1 host — Ubuntu 24.04 plus `systemd` and `systemd-sysv`, `CMD ["/sbin/init"]`, no goble code and no language runtime in it, and deliberately not `deploy/goblin/Dockerfile`, which is the stale k8s/distroless artifact — and `crates/goble-core/tests/install_systemd_e2e.rs` is the `#[ignore]`d test that drives it: it builds the image, runs it with `--privileged --cgroupns=host --tmpfs /run --tmpfs /run/lock -v /sys/fs/cgroup:/sys/fs/cgroup:rw -p 127.0.0.1:8787:8787`, builds a Linux `goblin` from this checkout in a Rust container (`-v "$PWD":/src`, `cargo build -p goblin-worker --release` — the worker, not the GUI, and a macOS host cannot produce the binary the unit's `ExecStart` needs), generates the script through the Rust API, copies the script and the binary to `$INSTALL_PATH/goblin.new` the way `provision_worker` does over SSH, runs the script as root, and then asks the host for the unit's state and the worker's health.
  - **Acceptance:** `cargo test -p goble-core --test install_systemd_e2e -- --ignored --nocapture` → **exit 0, 1 passed**; inside the fixture `systemctl is-active goblin.service` → `active` (and `is-enabled` → `enabled`), and `GET /health` on the published 8787 → `HTTP/1.1 200 OK` with `{"worker_id":"t3-worker","status":"Online","paired":true,…}`.
  - **It found a real defect.** The script chowned `$INSTALL_PATH` and `$WORKSPACE_ROOT` but not the data root above the workspace (`/var/goblin`), where the worker opens its task store and vault by default. On the fixture the unit started, the worker exited with `failed to open task store at "/var/goblin/tasks.db"` / `Error code 14: Unable to open the database file`, and systemd reported `activating` while it restarted. The install had never been run on anything, so nothing had ever said so. The script now creates and chowns `DATA_ROOT="$(dirname "$WORKSPACE_ROOT")"` as well, pinned by `test_the_install_gives_the_worker_the_data_root_it_is_told_to_use`.
  - **Which client:** the unit starts the worker with `--tls-bundle`, so 8787 is mTLS, not a plaintext port — `curl http://127.0.0.1:8787/health` inside the container answers `curl: (1) Received HTTP/0.9 when not allowed`. `/health` is therefore read by the test with `WorkerBundle::client_config` (the client configuration a paired desktop uses, so the response also proves the pairing chain) over the container's published port. `curl` cannot be that client at all: ring writes an identity's PKCS#8 with the public-key attribute (version 1) and the container's OpenSSL refuses to load it — `curl: (58) unable to set private key file: '/tmp/goblin-t3/client-key.pem' type PEM`, and `openssl pkey` says `unsupported`.
  - **Cannot settle:** a real VPS's distro and its already-installed packages; `APT` resolution on Debian vs Ubuntu (the fixture is Ubuntu 24.04, where the script's own `apt-get` branch runs, since the image ships no curl); whether the host's firewall permits 8787 from the client; and GitHub's runners, which have no privileged systemd container, so this stays a local command rather than a CI job.

- [x] **T4 — Verify a real RDP connection end to end.** The desktop direction's largest unproven piece: `RdpRemoteSource::connect` (`crates/goble-screen-sdk/src/lib.rs`, `rdp` feature) had no test that had ever decoded a frame from a live desktop. It does now, and the fixture's first run found the defect that made a frame impossible. `deploy/xrdp-host/Dockerfile` is an xrdp host — Ubuntu 24.04 plus `xrdp xorgxrdp xfce4 xfce4-terminal dbus-x11` (verbatim the packages `REMOTE_DESKTOP_STEP` installs) and the three the container needs to serve them: `dbus` (`dbus-daemon --system`, which `dbus-x11` alone does not provide), `procps` and `openssl`/`ca-certificates`. It creates the session account (`goble`), pins `/etc/xrdp/startwm.sh` to `exec startxfce4` the way the install script does, generates a self-signed `key.pem`/`cert.pem` pair, and `entrypoint.sh` starts `dbus-daemon --system --fork`, `xrdp-sesman` and `xrdp --nodaemon`. `crates/goble-screen-sdk/tests/rdp_e2e.rs` is the `#[ignore]`d test: it builds and starts that container itself on a free host port (or borrows one through `GOBLE_RDP_E2E_PORT`), polls readiness, builds a real `RemoteConfig`, calls the real `RdpRemoteSource::connect` against a real `ScreenRegistry`, and polls `registry.capture(<source>)` until the frame is a painted desktop.
  - **Acceptance:** `cargo test -p goble-screen-sdk --features rdp --test rdp_e2e -- --ignored --nocapture` (with `GOBLE_RDP_E2E_PORT=13389` if the container was started by hand) → **exit 0, 1 passed**, `decoded frame: 1024x768 (3145728 bytes, 786432 of 786432 pixels painted in 7827 colours, sample #000204 #000911 #000a08)`. The server's own side of that run, read from inside the fixture: `TLS connection established from ::ffff:172.17.0.1 port 63456: TLSv1.3 with cipher TLS_AES_256_GCM_SHA384`, `++ created session (access granted): username goble`, `Session started successfully for user goble on display 10`, `Starting the default window manager on display 10: /etc/xrdp/startwm.sh`, and behind the frame `ps -u goble` lists `xfce4-session`, `Xorg :10`, `xfwm4`, `xfce4-panel`, `xfdesktop`, `Thunar --daemon`.
  - **It found a defect in the client.** Without `ConfigBuilder::with_autologon(true)` the Client Info PDU carries no `AUTOLOGON` flag, and xrdp 0.9.24 then never starts a session for the account the client was handed: it draws its own login window instead, whose first bitmap update the engine cannot decode and the session ends before any `Image` event. The exact failure, with `GOBLE_RDP_E2E_LOG=debug`: after `session::x224 Got slow-path graphics update (11096 bytes)`, `rdp terminated: Err(Error { context: "decode error", kind: Decode(Error { context: "<ironrdp_pdu::basic_output::bitmap::BitmapData<'_> as ironrdp_core::decode::Decode<'_>>::decode", kind: NotEnoughBytes { received: 1808, expected: 44430 } }) })`, and `xrdp-sesman` logged no `created session` at all — xrdp's source gates on `client_info->rdp_autologin` (`xrdp_wm.c`, v0.9.24) and falls to `xrdp_login_wnd_create` without it. A viewer that was handed `RemoteConfig::username`/`password` has to log in with them, so the flag is now set unconditionally with that reason on the line. Two server-side variants were tried before the client was suspected, and both confirmed it was the client: `bitmap_compression=false` with `max_bpp=32` gave `read_graphics_update_type … unknown slow-path graphics update type` on a 1931-byte update, `max_bpp=16` gave `NotEnoughBytes { received: 244, expected: 54400 }` on a 7668-byte update, while a third-party client (`freerdp3-x11`, which sets the flag) drew the same fixture's Xfce desktop into a 1024x768 screenshot.
  - **It also found a readiness trap.** Docker's port forwarder accepts a host connection *before* anything inside the container is listening, so the first cold run's TCP poll "passed" against a server that was not up: `xrdp.log` showed no `connection received` line for either the poll or the client, and the client read a frame from a socket the forwarder then closed (`rdp connection failed: [read frame by hint …] custom error`). The poll now waits for xrdp's own `listening to port` line before it accepts a connection, on a container the test started.
  - **Why the pixels are asserted and a size is not enough:** `RdpCapturer` starts from `ScreenFrame::blank(source, width, height)` and restores that same blank on `ConnectionFailure`, so a non-empty buffer of exactly the requested dimensions exists before a single byte arrives and after every failed connection — a size assertion passes against a server that refuses every connection. The floor is higher than "one pixel" for the same reason at a smaller scale: xrdp paints its own connection-progress window first (30 144 pixels in 5 colours, measured), so the test waits for the settled desktop (786 432 pixels in ~7 800 colours) and the frame it asserts is the desktop, not the window.
  - **Cannot settle:** a real remote host's latency, NAT/firewall behaviour, and the pixels being *correct* (a frame that decodes is not a frame that looks right — the frame here is 7 827 colours of an Xfce desktop nothing in this repo drew, and no one looked at it). The dedicated desktop credential resolution from the client is `C3`'s item, not this one. And the fixture is macOS arm64 against an arm64 container with no emulation, so nothing here says anything about another architecture.
  - **Honesty note:** the item's escape hatch — leave `[~]` if xrdp cannot serve a session — was not needed: the fixture serves a real desktop and the client decodes it. What it can say is bounded: a decoded frame has arrived from a live xrdp session through the real source, at the dimensions the desktop carries.

- [ ] **T5 — the worker's always-on E2E test drains both pipes.** `crates/goblin-worker/tests/worker_e2e.rs` pipes the spawned worker's stdout (`.stdout(Stdio::piped())`) and never reads it, while the sibling test written in the same rollout drains both and says why (`runtime_isolation_e2e.rs`: the worker's tracing output goes to stdout). A child that fills the undrained pipe blocks, and nextest's timeout then fails the test that is now always on — and the CI job with it. Drain stdout the way the sibling does.

## Rules
- **A test that needs a fixture says so, and names the command that provides it.** `#[ignore]` is acceptable only for a test that genuinely cannot run in the default suite (a container, a privileged host), and then the owning doc and the tracker row must carry the exact command that runs it — an ignored test with no documented invocation is the bug T1 exists to fix.
- **Never weaken an existing assertion to make a new one pass.** If a test encodes the old behaviour, rewrite it and say why.
- **Claim what was run.** A verification that only exercised the protocol, the state or the YAML says exactly that; it is never reported as end-to-end.
